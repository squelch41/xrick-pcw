# Upstream source audit: Rick Dangerous I

Audited against `zpqrtbnk/xrick` master on 2026-11-06.

## Findings

The current upstream tree is not laid out as the earlier notes suggested. The repository root contains an `xrick/` directory; common code is under `xrick/src/`, and the first game's implementation is under `xrick/src/rd1/`. The second game is separate under `xrick/src/rd2/`.

Rick Dangerous I is the correct first target. Its engine is largely C, but the desktop build depends on SDL3 and a large platform layer. The current video backend in `xrick/src/sysvid.c` owns SDL window, renderer, texture and palette handling. The input backend in `xrick/src/syskbd.c` maps SDL scancodes. The time/sleep functions in `xrick/src/system.c` use SDL ticks and delay. These are replacement boundaries, not code to carry over to CP/M.

## Game framebuffer

The RD1 renderer is not a direct 320x200 bitplane renderer. `xrick/src/rd1/fb.c` declares a software framebuffer as `fb[FB_HEIGHT][FB_WIDTH]`; the drawing code documents a 320x200, 8-bit indexed framebuffer. The PC graphics path stores CGA-style two-bit colour values, expanded to one byte per logical pixel while drawing.

Important RD1 modules include:

- `draw.c`: drawing primitives and frame composition.
- `fb.c`: logical framebuffer and PC palette.
- `tiles.c`: 8x8 tile painting.
- `sprites.c`: sprite compositing, masks and clipping.
- `maps.c`, `scroller.c`: map and scrolling.
- `ents.c`, `e_*.c`: game entities and behaviour.
- `game.c`: game state machine and main loop.
- `dat_*.c`: embedded game data tables.

This is encouraging: the game logic and drawing routines are separated enough to define a native backend, but the existing draw path assumes a byte-per-pixel framebuffer and must be adapted.

## PCW display strategy to prototype

The PCW display is 720x256 monochrome. The source game is 320x200. A promising first fit is a 640x200 physical-pixel viewport centred horizontally (40-pixel side borders) and vertically (28-line top/bottom borders), using 2x horizontal replication and 1x vertical replication. Because PCW pixels are physically taller than they are wide, this preserves the source image's approximate 320:200 physical aspect ratio. This is a proposed mode, not yet measured on a real 9256.

The 2-bit source colour values must be converted to 1-bit output. Start with a fixed monochrome mapping derived from the PC palette and compare it with ordered dithering; dithering may improve gradients but can make small sprites and text noisy. Do not assume a full 320x200x8 framebuffer fits in the CP/M TPA. A packed 1-bit staging buffer is 8,000 bytes; direct drawing into PCW screen memory may save memory but requires careful Roller-RAM setup and restoration.

PCW video RAM is not a conventional linear framebuffer. Roller-RAM entries define the start address of each scan line, and the controller fetches bytes at eight-byte intervals. The initial implementation should avoid modifying Roller-RAM until a separate save/restore test has been written.

## Sound and controls

John Elliott's PCW hardware reference documents the dK'Tronics AY-3-8912 ports:

- `AAh`: select register.
- `ABh`: write selected register.
- `A9h`: read selected register.

AY register 14 is the joystick input/output port. The sound test should leave AY register 7 bit 6 clear so port A remains an input when joystick reads are needed. Sound effects can be generated by writing AY tone/noise/envelope registers; Atari ST YM2149 audio playback is not portable to this hardware.

The first input test uses CP/M BDOS function 6 for non-blocking console polling. That proves only CP/M keyboard input, not direct PCW keyboard scanning. Direct keyboard matrix access can be considered later if BDOS polling proves too slow or unsuitable for the game loop.

## Porting plan from this audit

1. Assemble and run the small CP/M sound/keyboard test on Joyce and the physical PCW.
2. Add a display diagnostic that saves/restores all video controller state and draws a bounded test pattern.
3. Build a packed monochrome blitter and benchmark it before porting the full draw layer.
4. Port a minimal RD1 room: static tiles, one controllable Rick sprite, collision and one screen transition.
5. Add sound effects and scrolling only after the room is playable.
